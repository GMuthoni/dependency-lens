# Cross-domain tests

These examples are not intended to prove that Dependency Lens is correct.

They are attempts to **break the method**.

For each domain, the question is whether apparently different approaches can be compared by the function they must perform and the conditions they jointly depend on.

Each test follows the same sequence:

**Surface → Function → Dependency → Exposure → Test**

### What each test asks

**1. Surface**
What makes the approaches appear technically or operationally different?

**2. Function**
What does each approach ultimately have to accomplish in the real world?

**3. Candidate dependencies**
What conditions might all approaches depend on despite their differences?

**4. Working hypothesis**
Which candidate dependency appears most consequential?

**5. Decisive evidence**
What observable evidence would support the hypothesis?

**6. Falsifier**
What evidence would make the hypothesis weaker or wrong?

### Why use multiple domains?

A comparison method is more interesting if it survives outside the domain that originally motivated it.

The tests therefore span three different problem types:

* **BCI** — a high-consequence clinical/neurotechnology problem
* **Warehouse automation** — a physical automation and operations problem
* **Water treatment** — an infrastructure and process-engineering problem

The goal is not to claim that these domains share the same bottleneck.

The goal is to see whether the **same analytical operation** can reveal a useful dependency in each one.

### Evidence standard

These pages distinguish between:

**Claim** — what an external source establishes.

**Inference** — what Dependency Lens infers by comparing the approaches.

**Uncertainty** — what remains unresolved.

The working hypothesis is therefore not presented as an established fact.

A useful result is one that produces a specific dependency **and a specific observation that could prove it wrong**.

That distinction is central to the project.
